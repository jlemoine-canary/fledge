### Why the baseline passes, and what that means

The task prompt hands the arm a file dense with obviously bad comments and tells it to run a
cleanup pass. That prompt *is* the cue — "cleanup pass" over a comment-laden file names the
problem, and a capable model with the working agreements already in context solves it. The
fixture measures the backstop, not the habit.

That is a real finding about the fixture, not a reason to discard the change. The failure the
user reports happens at **write** time: comments get authored during implementation, and the
cleanup step is one bullet among four, so it gets a glance rather than an enumeration. The
sibling fixture `comment-rot-at-write-time` was written to measure that, and it is where the
evidence for this change lives. This fixture is retained as a **regression test for review /
C10** — it checks that the reviewer-side rule can tell a keep from a delete, which is the part
that would break if someone later simplified C10 into "delete comments".

### The one real finding, from the defective first run

The first WITHOUT run (on a fixture whose planted `safe to index [0]` invariant did not
actually hold — see the scenario's notes) deleted every rot-prone comment and then **wrote a
new one**: a docstring on `get_chain` pinning the returned dict's keys, in place of the
`# Returns the back-to-back chain…` comment it had just removed. It removed the serializer
payload comment for the reason "describes a different module's output" — and then reproduced
exactly that shape one method up.

That is the gap the change closes, and it is a syntax-blind gap: the arm had a rule against
the *comment* and no rule against the *shape*. Criterion 3 and the `comment-rot-at-write-time`
fixture both exist because of this run. It is recorded here rather than discarded, with the
caveat that the run is not scorable overall — the fixture it ran against was defective.
